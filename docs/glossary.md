# 用語集 / Glossary

このカリキュラムで使用される技術用語の定義集です。各エントリは日本語名・英語名と説明を含みます。

---

## A

### ALB（Application Load Balancer）
**英語**: Application Load Balancer
**日本語**: アプリケーションロードバランサー

AWSが提供するL7（HTTPレイヤー）ロードバランサー。URLパス・HTTPヘッダー・クエリパラメータなどに基づいてトラフィックを振り分けることができる。このカリキュラムではstep05以降でALBを使用し、複数のEC2インスタンスに負荷を分散する。ALBにはヘルスチェック機能があり、不健全なターゲットへのトラフィックを自動的に止める。

---

## B

### Blue/Green デプロイメント
**英語**: Blue/Green Deployment
**日本語**: ブルーグリーンデプロイメント

現行バージョン（Blue）と新バージョン（Green）を同時に稼働させ、段階的にトラフィックを移行するデプロイ手法。問題が発生した場合でも即座にBlueへ切り戻せるため、デプロイのリスクを大幅に低減できる。このカリキュラムではstep11でALBの加重ターゲットグループを使い、step12でRoute53の加重ルーティングを使ってBlue/Greenを実装する。

---

## C

### Cache Aside パターン
**英語**: Cache Aside Pattern
**日本語**: キャッシュアサイドパターン / 読み取り時キャッシュパターン

アプリケーションがキャッシュを明示的に制御するキャッシング戦略。読み取り時はキャッシュを確認し（ヒット）、なければDBから取得してキャッシュに保存する（ミス）。書き込み時はDBへ書いてからキャッシュを削除または更新する。アプリケーション側に制御が集まるため実装が明確で、step04でRedisを使ってこのパターンを実装する。

### Circuit Breaker（サーキットブレーカー）
**英語**: Circuit Breaker
**日本語**: サーキットブレーカー / 回路遮断器

依存サービスの障害を検知して呼び出しを一時的に遮断するパターン。「CLOSED（通常）」「OPEN（遮断中）」「HALF-OPEN（試行中）」の3状態を持つ。障害が閾値を超えると OPEN になり、即座にエラーを返すことで障害の連鎖（カスケード障害）を防ぐ。このカリキュラムのstep13で実装し、DBやキャッシュの障害がアプリ全体を巻き込まないよう保護する。

---

## D

### DB シャーディング
**英語**: DB Sharding / Horizontal Partitioning
**日本語**: データベースシャーディング / 水平分割

データを複数のデータベースノード（シャード）に分散して保管する手法。シャーディングキー（例：`user_id % シャード数`）に基づいてデータをどのシャードに保存するかを決定する。各シャードが独立して稼働するため書き込みスループットをスケールできるが、クロスシャードJOINが困難になるトレードオフがある。step08で実装する。

### DNS TTL
**英語**: DNS Time To Live
**日本語**: DNS キャッシュ有効期限

DNSレコードがキャッシュされる時間（秒）。TTLが長いと変更の反映が遅くなるがDNSクエリ数が減る。TTLが短いと変更がすぐ反映されるがクエリ数が増える。Blue/Greenデプロイ時には切り替え前にTTLを短く（60秒など）設定し、切り替え後に元の値に戻すのが定石。step12で重要になる概念。

---

## E

### Expand-Migrate-Contract
**英語**: Expand-Migrate-Contract Pattern
**日本語**: 拡張・移行・縮小パターン

データベーススキーマをゼロダウンタイムで変更するための3フェーズ手法。まず「Expand（拡張）」で旧構造を維持しながら新構造を追加し、次に「Migrate（移行）」で既存データを新構造に移し、最後に「Contract（縮小）」で旧構造を削除する。各フェーズはロールバック可能なため安全に実施できる。step10で実践する。

---

## H

### ヘルスチェック
**英語**: Health Check
**日本語**: ヘルスチェック / 死活監視

サービスが正常に動作しているかを定期的に確認する仕組み。AWSのALBは登録されたターゲットに対して定期的に `/health` エンドポイントへHTTPリクエストを送り、HTTP 200が返らない場合はそのターゲットを「不健全（unhealthy）」とみなしてトラフィックを送らなくなる。このカリキュラムでは全アプリケーションに `GET /health -> {"status":"ok"}` の実装を必須としている。

### 水平スケーリング
**英語**: Horizontal Scaling / Scale Out
**日本語**: 水平スケーリング / スケールアウト

同一スペックのサーバーを複数台追加することで処理能力を増やす手法。対義語は垂直スケーリング。ALBと組み合わせることで無停止で台数を増減できる。サーバーがステートレス（セッション情報をサーバーローカルに持たない）であることが前提。step05から実践する。

---

## I

### 冪等性（べきとうせい）
**英語**: Idempotency
**日本語**: 冪等性

同じ操作を何度繰り返しても結果が変わらない性質。インフラのセットアップスクリプト（`setup.sh`）は冪等であるべきであり、誤って2回実行しても重複リソースが作成されたりエラーにならない設計が求められる。HTTP においては `PUT`・`DELETE` は冪等だが `POST` は冪等ではない。このカリキュラムではすべての `setup.sh` に冪等性が要求される。

---

## K

### k6
**英語**: k6 (pronounced "kay-six")
**日本語**: k6（ケーシックス）

Grafana Labs が開発したオープンソースの負荷テストツール。JavaScriptでシナリオを記述でき、VU（仮想ユーザー）数・テスト時間・スループット目標を柔軟に設定できる。`thresholds` でSLO（サービスレベル目標）を定義し、達成できない場合はexitコード1で終了する。このカリキュラムではすべてのステップにk6テストが付属している。

---

## R

### Read Replica（リードレプリカ）
**英語**: Read Replica
**日本語**: 読み取りレプリカ

プライマリDBのデータを非同期でコピーし、読み取り専用クエリを受け付けるDBインスタンス。プライマリへの読み取り負荷を軽減し、レポートや全文検索など重いクエリをオフロードできる。書き込みはプライマリのみに行う。レプリカラグ（データの遅延）が生じるため、更新後すぐに読み取る処理はプライマリから行う必要がある。step03で実装する。

### Redis
**英語**: Redis (Remote Dictionary Server)
**日本語**: Redis（レディス）

インメモリのキーバリューストア。文字列・リスト・ハッシュ・セット・ソート済みセットなど多彩なデータ構造をサポートし、データはメモリ上に保持されるため非常に高速（マイクロ秒オーダーのレイテンシ）。このカリキュラムではCache Aside パターンのキャッシュストアとして使用し、さらにALB配下の複数EC2でのセッション共有にも利用する。ElastiCache ではなく EC2 上のセルフホストでコストを抑える。

### Resolver パターン
**英語**: Resolver Pattern
**日本語**: リゾルバーパターン

シャーディングなど複数のデータソースが存在する場合に、リクエストをどのソースに振り向けるかを決定するロジックをResolver層として分離するパターン。アプリケーションコードからデータソース選択のロジックを切り離すことで、シャード数の変更やルーティングルールの変更を容易にする。step08のDB シャーディング実装で使用する。

---

## S

### Strangler Fig パターン
**英語**: Strangler Fig Pattern
**日本語**: ストラングラーフィグパターン / 絞め殺しの木パターン

既存のシステムを一気に置き換えるのではなく、新機能を新システムに実装しつつ古いシステムを段階的に縮小・廃止していく移行戦略。ALBのルーティングルールを使って新旧エンドポイントを振り分け、機能ごとに移行を進める。「絞め殺しの木（Strangler Fig）」という名前は、宿主の木を徐々に覆い隠しながら成長するツル植物に由来する。step09で実践する。

---

## T

### Terraform
**英語**: Terraform
**日本語**: テラフォーム

HashiCorp が開発したオープンソースの Infrastructure as Code（IaC）ツール。HCL（HashiCorp Configuration Language）でインフラの状態を宣言的に記述し、`terraform apply` で実際のクラウドリソースとして展開する。`terraform destroy` で作成したリソースを一括削除できるため、このカリキュラムのように一時的なリソースを扱う学習環境に最適。このカリキュラムのすべての AWS リソースは Terraform で管理する。

---

## V

### 垂直スケーリング
**英語**: Vertical Scaling / Scale Up
**日本語**: 垂直スケーリング / スケールアップ

既存のサーバーのCPU・メモリ・ストレージを強化することで処理能力を増やす手法。対義語は水平スケーリング。実施にはサーバーの再起動が伴う場合が多く、ダウンタイムが発生する。また、スペックの上限（最大インスタンスサイズ）という物理的な限界がある。step01で垂直スケーリングの限界を実測し、以降のステップで水平スケーリングへ移行する。

---

## Z

### ゼロダウンタイム移行
**英語**: Zero Downtime Migration / Online Migration
**日本語**: ゼロダウンタイム移行 / オンラインマイグレーション

サービスを停止させることなくデータベーススキーマ変更やシステム移行を行う手法の総称。Expand-Migrate-Contract パターンや Blue/Green デプロイメントがその代表例。本番システムでは計画メンテナンスのダウンタイムを設けることが難しいため、ゼロダウンタイムでの移行技術は現代のエンジニアに不可欠なスキルである。step10・step11・step12で実践する。
